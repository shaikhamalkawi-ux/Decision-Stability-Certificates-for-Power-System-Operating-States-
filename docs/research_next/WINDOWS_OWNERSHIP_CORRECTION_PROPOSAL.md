# Narrow future ownership correction — proposal only

The one closed harmless probe supports replacing the failed shared-job grouping with **one new kill-on-close Job Object per authenticated launcher/actual Python process**. The first fixed arm failed specifically when adding actual Python to the already-used new job (Win32 error5); the second fixed arm assigned each process to its own new job and deliberately terminated/reaped both successfully. These are host-specific observed capability results, not a proof of all future solver lifecycle behavior.

A future additive executor could retain the same token/hash handshake, exact parent relation, retained process handles/creation times and pre-backend ownership gate, while storing a list of separately owned jobs. It would close/terminate that list in reverse order, reap every retained handle and preserve individual assignment errors and memberships. Any ownership failure would still prevent backend import/optimization. No breakaway, removal or modification of outer jobs, privilege change or broad process-name kill is proposed. Captured hash-verified source loading and explicit final transport/source rehashes should remain part of its reviewed boundary.

This is an infrastructure change only. The existing batch source, failed run,336 saved seed proofs and attempted-call ledger must remain immutable. Whether a separately declared scientific executor may inherit the independently checked seed artifacts, and its exact remaining nomination/call/time budget, are decisions for the research lead before implementation. This proposal neither silently resumes that batch nor authorizes another seed evaluation, candidate, backend, optimizer call or capability probe. Any new executor still requires source/preparation/ownership review and explicit execution GO; harmless cleanup is not described as a tested scientific timeout.
